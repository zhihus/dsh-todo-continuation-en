- **Статус:** ПРОЕКТ, не утверждён, не реализован.
- **Дата:** 2026-09-09.
- **Базовый commit:** `d8fd147` (release: v0.6.0; тесты 64/64 по PLAN.md).
- **Источник:** обсуждение в рабочей сессии «Автоматизация настроек: рекомендация значений по

  автоподбору, оговорка об обратной связи) и запрос плана.
- **Назначение документа:** как у `PLAN-v0.3.0-advisory-templates.md` — постоянный артефакт для

  любые отклонения/дополнения согласуются отдельно и фиксируются здесь же.
- **Связь с PLAN.md:** после утверждения пункт вносится в `PLAN.md` как первый P-пункт нового

## 0. Цель изменения

Дать пользователю измеримый ответ на вопрос «какие значения настроек Todo Gate подходят моему
стилю работы», **не меняя ничего** — ни в коде плагина, ни в настройках. Новый офлайн-инструмент
`test/tune.mjs` читает те же durable-журналы сессий, что и `test/verify-live.mjs`, восстанавливает
по ним «жизненный цикл» каждого todo-списка (запись → напоминания → перепись или смерть), считает
статистику использования трёх числовых настроек и печатает рекомендацию с уровнем уверенности и
причиной — или честное «недостаточно данных». Принцип работы: **измерить → порекомендовать →
применить вручную → перемерить**. Автоматического применения нет и не будет (см. §11).

Ключевая гипотеза (проверяется самим инструментом на реальных логах, шаг 5 плана реализации):
по журналам можно восстановить enough статистики, чтобы рекомендация была информативной хотя бы
для части настроек. Если нет — штатный исход `insufficient`, а не угадывание.

## 1. Current implementation

- События журнала, нужные анализатору, уже наблюдаемы и уже парсятся в `test/verify-live.mjs`:
  `turn/start` (номер хода), `todo/write` (слепок списка со статусами), `compaction/summary`,
  `user/message` с `data.source.plugin === 'todo-continuation'` — каждое реальное подталкивание
  (и напоминание, и вето шлюза). Напоминание отличимо от вето по маркеру списка
  (`LIST_MARKER`/`carriesList`); «один и тот же неизменённый список» группируется `listBlock`.
- Тип напоминания (stale vs compaction) виден из `summary` notice-строки:
  `… (stale idle=N)` / `… (compaction id=…)`. Формат строки — не контракт хоста, парсить
  защитно (см. §9).
- Решения плагина (`skip:idle 2<5` и т.п.) в durable-журнале **не хранятся** — `logDecisions`
  пишет в лог хоста. Возможности срабатывания анализатор вычисляет сам реплеем порогов;
  in-memory кулдаун и quiet-режим из журнала не восстанавливаются — известное приближение (§5).
- Кандидаты на автоподбор (числовые настройки, читаемые `readConfig` в `index.js`):

| Настройка | Ключ | Дефолт | Наблюдаемая величина в журнале |
| --- | --- | --- | --- |
| Stale-todo prompt interval | `staleTodoPromptEveryNTurns` | 5 | простой списка к моменту переписи; доля переписей «сам» vs «после напоминания»; списки, умершие непереписанными |
| Stop-gate vetoes per turn | `gateMaxSteersPerTurn` | 2 | вето на ход (`user/message` без маркера списка) и исход хода: список закрыт в этом же ходе / ход упёрся в лимит |
| Per-list reminder cap | `maxPromptsPerList` | 0 | число напоминаний на один `listBlock` до переписи; P(ответ после k-го напоминания) |

- `gateSubagents` — политика, а не параметр: только отчёт по delegated-сессиям
  (`subagent/descriptor`), без числовой рекомендации.
- Инфраструктура: `decodeSessionFile` (multi-frame zstd, байточно-точный скан магии),
  `findSessions`, `cwdSlug`, `readLiveSettings`, маркерные функции живут в `verify-live.mjs`
  как скрипт с top-level кодом — импортом не переиспользуешь, только экстракция (§2.1).

## 3. Метрики (контракт вычислений)

Термин: **жизненный цикл списка (lifetime)** — от `todo/write` с незавершёнными пунктами до
следующего `todo/write` (перепись) или до конца сессии (цензурировано).

`listLifetimes(events)` → по каждому lifetime:

| Поле | Смысл |
| --- | --- |
| `outcome` | `natural` (следующий `todo/write` без напоминания в окне) / `stale-prompted` / `compaction-prompted` / `unknown-prompted` (напоминание было, тип не распознан) / `censored` (конец сессии без переписи) |
| `idle` | для переписи: `turn(переписи) − turn(записи)`; для censored: `turn(последнего turn/start) − turn(записи)` (нижняя граница) |
| `latency` | только prompted: `turn(переписи) − turn(последнего напоминания в окне)` |
| `advisoriesInWindow` | сколько напоминаний доставлено в окне |

`vetoTurnOutcomes(events)` → по каждому ходу с ≥1 вето: `turn`, `vetoes`, `reachedCap`
(`vetoes ≥` текущего капа из settings.yaml), `completedInTurn` (существует `todo/write` этого
хода после первого вето с нулём незавершённых) / иначе `unfinishedSurvived`.

`advisoryGroups(events)` → по каждой личности списка (`listBlock`, в порядке доставки):
число напоминаний и `answeredAfterK` — произошла ли перепись этого списка после k-го напоминания
до следующего напоминания группы / конца сессии. Компакционные и stale-напоминания одного списка
группируются вместе — вопрос всегда один: «список вернули и на него ответили?»

Агрегация: пул по выбранным сессиям **плюс** построчная таблица per-session (как в verify-live),
чтобы аномальные сессии были видны. Delegated-сессии (`subagent/descriptor`) исключаются из пула
по умолчанию (`--include-subagents` возвращает), т.к. живут по другой политике гейта.

## 4. Правила рекомендаций (начальная калибровка)

Числа ниже — сознательно консервативная стартовая калибровка; пересматриваются по результатам
первого прогона на реальных логах (шаг 5). Вердикты: `keep` / `lower` / `insufficient`
(повышать значения по данным нельзя — см. цензуру в §5).

**Пороги достаточности** (ниже — `insufficient`, с указанием, сколько не хватает):
`MIN_LIFETIMES = 30`, `MIN_DEAD = 10`, `MIN_VETO_TURNS = 20`, `MIN_CAP_CELL = 10`,
`MIN_GROUPS = 10` (групп с ≥2 напоминаниями), `MIN_TAIL_CELL = 8`.

**`staleTodoPromptEveryNTurns`** (`recommendInterval`):
1. lifetimes < `MIN_LIFETIMES` → `insufficient`.
2. censored-списков с idle выше текущего интервала ≥ `MIN_DEAD` → `lower` (текущий − 1, min 1):
   «списки умирают, несмотря на напоминания; напоминать раньше».
3. stale-prompted ≥ 30% переписей и медиана `latency` ≤ 1 → `keep`: напоминания на текущем
   интервале отвечаются ходом в пределах одного хода.
4. prompted-stale почти нет (< 10% lifetimes) и медиана natural idle < интервала → `keep`
   с пометкой «канал инертен: модель обновляет список сама раньше интервала».
5. иначе `keep` с confidence `low`.

**`gateMaxSteersPerTurn`** (`recommendVetoCap`):
1. ходов с вето < `MIN_VETO_TURNS` → `insufficient`.
2. текущее 0 → `keep` (выключено пользователем намеренно).
3. выборка ходов с `vetoes == current` ≥ `MIN_CAP_CELL` и
   P(complete | v==current) < 0.2 × P(complete | v==1) → `lower` (текущий − 1): последнее вето
   почти никогда не доводит список до закрытия.
4. иначе `keep`. Если доля `reachedCap` высокая — печатать заметку «повышение капа по данным
   не измерить (кап сам цензурирует выборку), только ручной эксперимент».

**`maxPromptsPerList`** (`recommendPerListCap`):
1. групп с ≥2 напоминаниями < `MIN_GROUPS` → `insufficient`.
2. наименьшее k с P(ответ | напоминание №k) < 0.1 при выборке ≥ `MIN_TAIL_CELL` →
   рекомендация `cap = k − 1` (включение опционального капа; от дефолта 0 это не «шаг», а
   включение функции — печатать явно).
3. такого k нет → `keep 0`: ответы приходят даже на поздние напоминания, кап не нужен.

**Confidence** (`high`/`medium`/`low`) — от объёма выборки относительно порогов:
≥ 3× порога → `high`, ≥ 1× → `medium`, между — вердикт не выдаётся вовсе.

**Формат вывода** (блок на настройку; `--json` отдаёт те же поля структурой):

```
Stale-todo prompt interval — current: 5
  lifetimes 41: natural 24, stale-prompted 9, compaction-prompted 6, censored 2
  natural idle: median 3 (p25 2 / p75 5) | stale latency: median 1
  died despite reminders: 2 (median idle 9)
  → KEEP 5 (confidence: medium) — reminders at this interval are answered within 1 turn
```

## 5. Честность анализа (обязательный эпилог каждого вывода и README)

1. **Цензура текущей настройкой.** Журналы собраны при текущих значениях; контрфакта («а было
   бы при 3») в данных нет. Рекомендации — относительные, шаг ±1 (для per-list cap — включение
   капа), а не «оптимум».
2. **Корреляция ≠ причина.** Перепись после напоминания не обязательно следствие напоминания
   (компакция, собственный цикл модели).
3. **In-memory состояние не восстанавливается**: кулдаун и quiet-режим не видны в журнале,
   число «возможностей» приблизительно; категория `censored` считается по факту отсутствия
   переписи, а не по отсутствию напоминания.
4. **Малые выборки лгут** — поэтому пороги §4 и честный `insufficient`.
5. **Петля**: после применения рекомендации — перемерить (`tune` на свежих логах с `--since`).
6. tune.mjs **никогда не меняет настройки** — только печатает (инвариант §11).

## 9. Risks

1. **Цензура/обратная связь** — главная угроза валидности рекомендаций (§5.1). Митинг: шаг ±1,
   явный дисклеймер в каждом выводе, петля «применить → перемерить», запрет авто-применения.
2. **Парсинг `summary`** notice-строки: формат не является контрактом хоста; парсить защитно,
   нераспознанное → `unknown-prompted` (выборка не теряется, категория честная).
3. **In-memory кулдаун/quiet не видны в журнале** — число возможностей завышено (§5.3);
   решение уже вшито в определение категорий (по факту переписи, не по факту напоминания).
4. **Экстракция verify-live** может незаметно сломать аудиторский инструмент; митинг — T12
   побайтовое сравнение до/после.
5. **Разнородность сессий** (быстрые вопросы vs длинные имплементации) усредняется в пуле;
   per-session таблица сохраняется в выводе, пул — только для вердикта.
6. **Мало данных у конкретного пользователя**: `insufficient` — штатный исход; инструменту
   запрещено «выжимать» рекомендацию из шума (пороги §4).
7. **Subagent-сессии** искажают статистику (другая политика гейта) — исключены по умолчанию.

## 11. Утверждённые ограничения и инварианты

- `test/tune.mjs` и `test/lib/*` — **только чтение** (журналы, `settings.yaml`); ни одной
