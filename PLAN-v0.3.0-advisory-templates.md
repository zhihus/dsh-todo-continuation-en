# План v0.3.0 — Редактируемые advisory-шаблоны сообщений

- **Статус:** УТВЕРЖДЁН, не реализован.
- **Дата утверждения:** 2026-09-06.
- **Базовый commit:** `c9333a2` (v0.2.0, тесты 14/14 зелёные).
- **Источник:** утверждённый план из рабочей сессии («Анализ и план: редактируемые advisory-шаблоны (v0.3.0)»).
- **Назначение документа:** постоянный артефакт для сверки фактических изменений реализации с утверждённым планом. Реализация не должна отклоняться от этого плана; любые отклонения/дополнения согласуются отдельно и фиксируются здесь же.

## 0. Цель изменения

Текст advisory-сообщений плагина (подсказок модели по работе с todo-списком) должен стать редактируемым через настройки плагина: текст отделяется от кода, хранится как настройка и редактируется на странице настроек. Логика определения момента отправки advisory не меняется вообще. Принцип: «было — код сам формирует текст; станет — код берёт шаблон из настроек и подставляет те же значения».

## 1. Current implementation

Advisory-сообщений два, они реально разные (`index.js`):

| Сообщение | Функция | Семантика | Структура |
|---|---|---|---|
| No-todo | `noTodoPromptMessage(everyNTurns)` (:63–68) | «начни использовать todo для многошаговой работы» | однострочный абзац |
| Stale | `staleTodoPromptMessage(everyNTurns)` (:70–79) | «освежи статусы, **не создавай** новую работу» | многострочный (+`\n\n`), нумерованный список из 2 альтернатив |

- Placeholder-системы сейчас нет. Единственная интерполяция — JS template literal `${everyNTurns}` внутри двух builder-функций. Подстановка — в точках вызова: `agent.steer(steerMessage(noTodoPromptMessage(cfg.noTodoEvery)))` (:160) и `steerMessage(staleTodoPromptMessage(cfg.staleEvery))` (:171). В текст попадает только одно динамическое значение — эффективный интервал соответствующего advisory; других динамических данных (номер turn, размер списка) в текстах нет.
- `readConfig()` (:97–103) читает только интервалы; `0 = disabled` гейтится условиями `cfg.*Every > 0` (:156, :167) — при выключенном advisory шаблон вообще не вычисляется.
- Schema (:115–118): `Schema.number().default(...)` для интервалов; регистрация в try/catch (:109–123), при сбое → `scope = null` → `readConfig` отдаёт встроенные дефолты (существующий путь деградации).
- Инфраструктура настроек (проверено по исходникам `@deepseek-ai/dsh-settings` + `dsh-client-ui-settings`): при регистрации schema резолвит сохранённую секцию (reject → throw → наш catch); при каждой записи `update()` мержит user-слой поверх `base` и прогоняет через schema **до** персистенции (`resolve()` = `schema(mergeLayers(base, section))`); инвалидная секция при живой перезагрузке файла → «keeping last good» + warn; браузерный scope зеркалирует `describe()` с ре-гидрацией schema, отклонённая запись → recovery read, снапшот держит последнее валидное значение. Клиентский `numberField` пре-валидирует (`>= 0`) перед `scope.set` (client.js:57–60).
- Эмпирика (schemastery 3.18.0, проверено прогоном): `Schema.string().default(X).pattern(/\{n\}/)` — ключ отсутствует → default; `null` → default; невалидная/пустая строка → throw `expect string to match regexp /\{n\}/`; повторы, мультистрочность, лишний текст вокруг placeholder, неизвестные ключи секции — OK.

## 2. Required settings

**Два отдельных шаблона**, а не один общий:

- `noTodoPromptTemplate` (string) — текст no-todo advisory;
- `staleTodoPromptTemplate` (string) — текст stale advisory.

Обоснование: два разных события с противоположными инструкциями модели («создавай список» vs «не создавай, только обнови статусы») и разной структурой (строка vs многострочный список). Один общий шаблон потребовал бы держать оба промпта в одном поле с непонятной маршрутизацией; текущий код уже имеет две отдельные функции — шаблоны ложатся на них 1:1, усложнения нет.

## 3. Placeholder contract

| Template | Placeholder | Значение | Источник | Required |
| -------- | ----------- | -------- | -------- | -------- |
| `noTodoPromptTemplate` | `{n}` | эффективный интервал no-todo advisory | `cfg.noTodoEvery` из `readConfig(scope)` (schema-resolved `noTodoPromptEveryNTurns`; при `0` advisory выключен и шаблон не читается) | да |
| `staleTodoPromptTemplate` | `{n}` | эффективный интервал stale advisory | `cfg.staleEvery` аналогично | да |

Контракт:

- **Подстановка**: literal `split('{n}').join(String(n))` — без template engine; повторные `{n}` заменяются все.
- **Неизвестный placeholder** (`{foo}`): остаётся в тексте как есть, ошибкой не считается (протестировано).
- **Повторное использование**: каждое вхождение получает одно и то же значение.
- **`{ n }` (с пробелом)**: не матчится паттерном → сохранение отклоняется; в подсказке GUI явно указан синтаксис «ровно `{n}`».
- **`{{n}}`**: проходит валидацию (содержит `{n}`), рендерится как `{{5}}` — задокументированное поведение без спец-обработки.
- **Отсутствие обязательного `{n}`**: шаблон невалиден (см. §4). Других placeholder не вводится — других динамических значений в сообщениях нет.

## 4. Validation

Трёхуровневая, штатными механизмами:

1. **Schema (авторитетный)**: оба поля как `Schema.string().default(<дефолт>).pattern(/\{n\}/)`. Любая запись через settings-инфраструктуру (GUI `scope.set`, `settings mutate`) резолвится через schema **до** персистенции — шаблон без `{n}` не сохранится, ошибка `expect string to match regexp` вернётся в GUI, mirror останется на последнем валидном значении.
2. **Клиент (UX)**: контрол секции держит локальный draft; невалидный draft → inline-подсказка «Template must contain required placeholder {n}» рядом с полем, `scope.set` не вызывается. Убирает churn отклонённых записей при наборе и даёт мгновенную обратную связь.
3. **Runtime (страховка)**: `readConfig` принимает шаблон только если это строка, содержащая `{n}`, иначе — встроенный дефолт. Через валидные пути недостижимо (schema отсекает раньше), но закрывает гипотетические обходные записи.
4. **Ручная правка settings.yaml** с инвалидным шаблоном: при старте `register()` бросит → существующий путь деградации (`scope = null` → весь namespace на встроенных дефолтах, включая интервалы) + диагностический лог; при живой перезагрузке — «last good» + warn. Задокументировать в README.

## 5. Backward compatibility

- Старый `settings.yaml` без новых ключей → schema отдаёт дефолты → тексты **побайтово равны текущим** (builder-функции удаляются, `renderTemplate(DEFAULT_X, n)` === старый вывод; тесты фиксируют точное равенство со строками-литералами).
- Логика срабатывания не трогается: счётчики, cooldown-и, per-turn dedup, ветка `todos !== undefined`, hard gate, `steerMessage`, `PLUGIN_SOURCE` — без изменений; меняются только две точки построения текста.
- Имена/дефолты интервалов, семантика `0 = disabled` — без изменений; при `0` шаблон не читается вовсе.
- Неизвестные ключи в секции проходят schema (проверено эмпирически) — чужие/старые ключи не ломаются.

## 9. Risks

1. **Набор текста vs autosave** (выявлено из client.js:57–60): посимвольный `scope.set` для textarea давал бы частые отклонённые записи в промежуточных невалидных состояниях («удалил `{n}`, ещё не дописал»). Митинг — draft + коммит только валидного + inline-ошибка; остаточный: пользователь обязан восстановить `{n}` до сохранения — это и есть требование.
2. **Ошибки schema в GUI**: отклонение хостом надёжно (запись не persists, mirror на last good), но подсветку ошибки рендерит наш собственный контрол (generic shell за нас это не сделает) — поэтому проверка дублируется на клиенте.
3. **`{ n }`/`{{n}}`**: первый отклоняется как невалидный (ожидаемо), второй проходит и рендерится как `{{5}}` — задокументировать в подсказке и README.
4. **Ручной yaml с инвалидным шаблоном**: рестарт деградирует **весь namespace** на дефолты (включая интервалы) — это существующая семантика loud-fail, но с более широким радиусом; описать в README upgrade-note.
5. **Многострочные шаблоны в settings.yaml**: dsh-settings требует JSON-совместимость (строки с `\n` проходят), YAML-сериализация закавычивает автоматически; риск низкий, покрыт ручным round-trip чеком.
6. **Пользовательский текст меняет поведение модели** — это цель фичи, но плохой шаблон может ослабить advisory; дефолт всегда доступен сбросом настройки к дефолтному значению.

## 10. Out of scope

Обнаружено при анализе, в задачу не включено:

- Редактируемый continuation message hard gate (явно исключено заказчиком; ранее был в roadmap 0.3.0 — теперь отдельное решение);
- Placeholder'ы `{turn}`/`{session}`/`{todoCount}` (данных для них в сообщениях сегодня нет);
- Локализация шаблонов;
- Система управления промптами (история/A-B);
- Hook-cancel containment (кандидат 0.2.1), event-log cursor, subagent detection;
- Рефакторинг `numberField` в общий компонент сверх необходимого.

## 11. Утверждённые ограничения и инварианты

- **Не менять**: условия срабатывания advisory; счётчики turns; todo snapshot; hard gate; событие `agent/turn-stopping`; `agent.steer()`; поведение `ask_user_question`; stop-gate для незавершённых todo; существующие значения по умолчанию; существующие имена настроек; семантику `0 = disabled`.
- **Обратная совместимость**: если пользователь не редактировал новый шаблон, результат — тот же текст, что и до изменения (`default template + стандартные значения` = текущий prompt побайтово).
- Placeholder ровно один на шаблон — `{n}`; не использовать сложный template engine; простейшая корректная реализация в существующей архитектуре.
- Два отдельных шаблона (по одному на advisory), не один общий.
- Обязательный placeholder не удаляем: невалидный шаблон нельзя сохранить; ошибка — штатным механизмом валидации настроек, а не после отправки сообщения.
- Публичный API плагина (`name`, `inject`, `apply`, namespace `todo-continuation`, `cordis.patch.yml`) не меняется.
- Плагин идентифицируется `package.json` name — не менять.
- Языки: отчёты пользователю — русский; код/комментарии — английский; дисциплина RED→GREEN («no test, no code»).
- Деплой (push, reinstall, рестарт DSH) — только по отдельному подтверждению пользователя; рестарт `dsh web` делает пользователь.
