# PLAN.md — план развития `dsh-todo-continuation`

Рабочий документ. Английский `README.md` — источник истины для пользователя; этот файл —
очередь изменений и контракт каждого пункта.

## Контекст

v0.5.0 починила две структурные поломки: состояние «есть ли действующий список и сколько
он простаивает» теперь восстанавливается из durable-журнала сессии (переживает рестарт,
резюм и компакцию), а само напоминание приносит список модели. Осталось то, что v0.5.0
осознанно не делала: точка доставки (только граница остановки), слепота к компакции как
событию, отсутствие объяснений «почему молчит» и несколько мест, где настройка может
восстановить старый баг.

## Нецели (постоянные)

* Плагин не создаёт, не завершает и не переписывает todo — автор списка только модель.
* Никакого «подтолкни модель к планированию»: сессия без `todo/write` не получает ничего.
* Ни один механизм не должен уметь блокировать ход без верховного лимита и без выхода
  (`abort` пользователя вне игры).
* Не трогаем состояние других сессий и чужие namespace настроек.

## Правила игры

1. Каждый пункт = отдельно проверяемое изменение: код → тест(`node test/todo-continuation.test.js`)
   → `README.md` → `README.ru.md` / `README.zh.md` синхронно к релизу.
2. Всё, что можно вывести из журнала сессии, выводится из журнала, а не из памяти процесса.
   В памяти живут только лимиты частоты и локальный счётчик вето.
3. Любая деградация (невалидная настройка, недоступный namespace) — громкая, с текстом в логе.
4. Релиз: `release:`-коммит, аннотированный тег, `git push en && git push en vX.Y.Z`
   (коммит/тег/пуш делает человек). Копия в `~/.dsh/profiles/web/node_modules` — только
   как временный синхрон, живёт до ближайшего `pnpm install`.
5. Пункты P1–P4 = **v0.6.0**; P5–P6 = **v0.7.0**; P7–P8 релиза не требуют.
   *Поправка (09.09):* P5–P6 оказались сделаны в том же подходе, что и P1–P4, и
   разграничения коммита между ними нет — они включены в **v0.6.0** вместе со всеми.
   Следующая граница релиза: P-пункты, которых ещё нет в этом плане.

## Чек-лист релиза (P8)

Перед тем как отдать изменения хосту:

1. `npm run verify` — синтаксис обеих сторон + полный прогон тестов (сейчас 64/64).
2. Документация синхронна: `README.md` (источник истины) → `README.ru.md` →
   `README.zh.md`; новые ключи есть в таблицах и в `client.js`, их подписи и
   search-элементы совпадают с текстом раздела.
3. `package.json`: `version` + описание; `files` покрывает все раздаваемые файлы.
4. `release: vX.Y.Z`-коммит, аннотированный тег, `git push en && git push en vX.Y.Z`
   — это делает человек, не плагин-агент.
5. Живой профиль: `pnpm install` в `~/.dsh/profiles/web` (или `link:<путь>` в
   `cordis.patch.yml`, если разработка идёт из рабочей копии). Синхрон копией в
   `node_modules` — только временный мост: он живёт до ближайшего `pnpm install` и
   не переживает его.
6. **Рестарт DSH обязателен**: процесс держит старый модуль в памяти, и никакая
   правка на диске не видна, пока он не перезапущен. `client.js` дополнительно
   требует перезагрузки страницы (а без запущенного `pnpm run dev:web` — ещё и
   пересборки бандлов).
7. Проверка «а точно работает»: `todo-continuation.logDecisions: true` в
   `settings.yaml`, затем одна граница остановки — в логе должна появиться строка
   `[todo-continuation] … at=stop-boundary …`. Её нет — проблема в монтаже, а не в
   логике. Строка есть — видно по какой причине что произошло.

### Что план не предвидел (по уроку на будущее)

- **Имя поля важнее логики.** Ветка P1 проверяла `standing.compactionAfterWrite`,
  обход журнала возвращал `compactedAfterWrite`: триггер не срабатывал ни разу и ни о
  чём не сообщал. Единственная нормальная защита от этого — P3, затем и сделанный.
- **Пункт P4 про `{todos}` оказался уже сделан** в P1 (`renderAdvisory` допечатывает
  список, если шаблон его потерял), так что от P4 остались clamp и мёртвые ключи.
- **Кэш обхода журнала ключён размером лога**, а состояние — id сессии. В прод-коде
  коллизия невозможна, но тест, переиспользовавший `session-1` для двух разных
  фейковых сессий, подмешал один список в другой. Тестам с несколькими фейковыми
  сессиями нужен отдельный id на каждую.
- **Живой процесс грузит модуль один раз**: синхрон копии в `~/.dsh/profiles/web`
  ничего не меняет до рестарта, а `client.js` — до пересборки/перезагрузки страницы.
  Проверять «не работает ли плагин» без учёта этого бессмысленно.

## P1. Компакция как триггер напоминания (не ждать N ходов)

**Проблема.** DSH заменяет диапазон истории одним summary-узлом; вместе с ним из контекста
уходит и копия туду-листа. Сейчас об этом знает только счётчик простоя: модель может
простоять без списка один ход и получить напоминание лишь через N.

**Контракт.** Если после последнего `todo/write` в журнал легла компакция
(`compaction/summary` с `compactionId`, которому соответствует `compaction/end` без `error`;
замена — идущий сразу `user/message` с `source.plugin === 'compact'`), а действующий список
всё ещё содержит незавершённые пункты — вручить список модели немедленно, независимо от
`staleTodoPromptEveryNTurns` и кулдауна простоя.

**Новое конфигурирование.**

| Ключ | Тип | Дефолт | Смысл |
| --- | --- | --- | --- |
| `promptAfterCompaction` | boolean | `true` | вручать список сразу после приземления компакции |
| `compactionPromptTemplate` | string | встроенный текст | текст этого напоминания; обязательных placeholder нет |

Placeholder'ы: `{todos}`, `{total}`, `{unfinished}`, `{n}` (фактический простой в ходах).
Компакцию идентифицируем по `compactionId`: один `compactionId` → не больше одного
напоминания, даже если событийных границ хода между ними несколько.

**Тесты.** компакция без последующего `todo/write` → один сигнал с `{todos}`; тот же
`compactionId` повторно не срабатывает; компакция после закрытого списка → молчим;
`promptAfterCompaction: false` → молчим; компакция в журнале до старта плагина (рестарт) →
сигнал на первой же границе; `compaction/end` с `error` → не сигнал (неудачная попытка ничего
не стирала).

## P2. Доставка в середине хода, а не только на границе остановки

**Проблема.** `agent/turn-stopping` не вызывается, если ход кончился ошибкой (429), отменой
или непрерывным потоком инструментов. Именно поэтому живой зонд в хосте ничего не показал.
Даже когда граница достижима, модель получает список в тот момент, когда ход уже закрыт.

**Контракт.** Второй канал доставки: сериальное расширение `tools/post-execute`
(`dsh-tools`: `ctx.on('tools/post-execute', function (exec, result, next) { ... })`,
решение `PostToolDecision` с `additionalContexts?: UserMessage[]`). Не позже чем после
первого инструмента хода, где выполнено условие P1 или условие простоя, приложить список
через `additionalContexts`. Источник контекста — `plugin: 'todo-continuation'`, чтобы след
был различим в журнале.

**Правила частоты.** Один mid-turn контекст на ход и на причину; лимиты и счётчики — те же
in-memory состояния, что и у advisory; граница остановки по-прежнему может выдать напоминание,
если причина появилась позже.

**Тесты.** срабатывает ровно один раз за ход; `next()` вызывается обязательно и его решение
не меняется (гейт-ветки не трогаем); отсутствие инструментов в ходу → ничего (fallback на
границу остановки); контекст содержит список; источник атрибутирован плагину.

**Риск.** Нужно подтвердить на типе `PostToolDecision`, что `additionalContexts` легитимен
в возвращаемом решении, а не только во вложенных вариантах, и что скоуп `this: Scoped<ToolRuntime>`
даёт доступ к `agent`/`session` конкретного сабагента.

## P3. Диагностика: плагин объясняет, почему промолчал

**Проблема.** «Почему не напомнил?» сейчас отвечается форензикой `session.jsonl.zstd` — час
работы на вопрос из одной строки.

**Контракт.** Новый ключ `logDecisions` (boolean, дефолт `false`). Когда включён, на каждой
границе хода пишется одно решение с причиной: `gate:block` / `gate:cap-reached` /
`prompt:idle n=N` / `prompt:compaction id=…` / `skip:no-list` / `skip:no-unfinished` /
`skip:idle N<cfg` / `skip:cooldown` / `skip:already-prompted`. Уровень — `debug`, в штатном
режиме тишины не нарушаем.

**Тесты.** включённый флаг даёт ожидаемую строку для каждой ветки; выключенный — ноль записей;
никакая ветка не бросает из-за отсутствующего логгера.

## P4. Защита настроек от самого себя

* `gateMaxSteersPerTurn` — clamp/верхняя граница (не больше 10): опечатка не должна
  возвращать бесконечное вето.
* Шаблон без `{todos}` → список допечатывается блоком после текста (напоминание не может
  остаться «пустым» из-за редактирования текста).
* Неизвестный placeholder остаётся как есть, но попадает в `logDecisions`-строку.
* Если в пользовательских настройках лежит мёртвый `noTodoPromptEveryNTurns` — один раз
  в логе сказать, что ключ более не существует.

**Тесты.** кап 1000 → фактически 10; шаблон без `{todos}` → текст + блок списка; наличие
мёртвого ключа → ровно одно предупреждение.

## P5. Адаптивный отступ, если напоминание игнорируют

После двух подряд сигналов без единого `todo/write` — тишина до изменения самого списка или
новой компакции; факт перехода в тихий режим один раз в лог. Цель: не превращать плагин в
фоновый шум, который модели перестают читать.

## P6. Политика для сабагентов

Исследовать, как из payload `agent/turn-stopping` / `tools/post-execute` надёжно отличить
делегированный агент (сабагент не может спросить пользователя — `DELEGATED_CALLER`), и
добавить `gateSubagents` (boolean, дефолт `true`): при `false` — не вето на сабагентах,
контекст-напоминания остаются.

## P7. Апстрим: действующий план должен переживать `turn/start`

Плагин обходит дыру в хосте: DSH гасит `todos`-проекцию на каждом `turn/start`, хотя последний
снимок лежит в журнале. Задача — не код, а офер в репозиторий DSH: перематериализовывать
последний план в начале хода (или хранить его в метаданных сессии). Результат — пункт
«документ/заметка в репозиторий + ссылка из README», после которого часть P1/P2 может стать
тоньше.
